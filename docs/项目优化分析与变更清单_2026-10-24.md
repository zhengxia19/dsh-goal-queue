## 2. 为什么会话数量有时刷新、有时不刷新

### 2.1 已纳入的会话与新出现的会话走了不同路径

[Coordinator.start / hold / scanRunning](../src/client/coordinator.ts) 中：

- 已纳入的 Session 会被 `hold()` 订阅，状态变化触发 `observe()`，结束后更新占用。
- Session 目录变化的订阅只调用 `syncTitles()`，不会发现新运行的 Session。
- `discover()` 主要由打开面板或点击“刷新运行任务”触发。[QueueBoard 的发现 effect](../src/client/QueueBoard.tsx) 只依赖面板开关和配置读取状态。

因此，已纳入任务的状态更新与新增外部任务的发现不是同一能力。R01 证明了这个差异；不能把当前侧栏“运行 N”理解为实时系统总会话数。

### 2.2 “首次读到过目录”不等于“本次刷新成功”

已安装官方 SDK 的 `lib/client.js`：

- `refreshList()`（约 3245–3290 行）在业务错误或已识别传输错误时记录内部 `listState/listError`，可以正常结束 Promise。
- `phase` 只表示是否至少成功取得过一次目录；之后刷新失败不把 `ready` 改回 `pending`。这一语义也写在 `lib/types/client/sessions/manager.d.ts`。
- 对外 `SessionListState` 和 `projectList()`（约 4146 行）没有投影内部 `state/error`。

当前 `scanRunning()` 只做 `await sessions.refresh()` 和 `snapshot.phase === 'ready'` 检查。这不足以证明本次拿到了新目录。

**实现限制：不能简单增加 `sessions.list.getSnapshot().state` 检查，该字段不属于当前公开契约。** 应评估通过现有公开 `remote.session.list({}, signal)` 的 `RemoteResult` 确认新基线，再与 `sessions.refresh/list/retain` 的公开状态协调；返回类型可见已安装 SDK 的 `lib/typert.remote-client.d.ts`。不访问私有 manager，不补丁 Desktop，不将额外 RPC 成功误称为全局并发锁。

### 2.3 首次发现缺少明确的初始化就绪信号

`settings.status=ready` 与 `Coordinator.booted=true` 之间可能还有恢复 CAS。此时界面可以触发发现，但 `scanRunning()` 会拒绝；`booted` 改变又不会使 Board 的发现 effect 重跑。R03 覆盖了延迟恢复 CAS 的入口，Desktop 时序仍待验证。

建议将初始化就绪、发现进行中、上次成功同步、同步失败分别表示；调度器就绪后安排首次只读发现。目录中运行身份变化触发合并发现，避免每次标题或 retain 计数变化都全量扫描。扫描中收到新变化应安排下一轮，不能因复用同一个 Promise 丢掉变化。

自动发现仅恢复观察。读取恢复成功不恢复派发授权；发现失败时停止新增派发并显示真实同步状态。定时补读如确有必要，应先测量读取成本，再设有限频率和失败退避。

## 3. 额外发现：原 Goal 身份可能被替换（优先修复）

路径：`scanRunning()` 读取当前 Goal → [adopt()](../src/queue.ts) 对 interrupted 任务使用 `data.goalId ?? t.goalId` → [observeTask()](../src/client/observe-task.ts) 按已被替换的 Goal ID 判断完成。

R05 的最小场景：

1. 队列旧任务指向 Session S、Goal A，状态 interrupted。
2. 用户在 Session S 内运行了另一个 Goal B。
3. 插件重新发现 S，把旧任务及其当前 Attempt 的 Goal ID 改成 B。
4. B 完成且 S idle，旧任务被标为完成。

这是完成证据归属错误。不能只在 `resumeGoal()` 中校验身份，而允许自动发现路径改掉身份。

建议：同一 Session 不代表同一执行。旧 Goal ID 与新投影不符时保留旧任务、旧 Attempt 的证据，将新活动作为独立观察占用；提示用户检查。不得将 B 的完成认作 A 完成。仍在运行的历史普通 Session 也不应在缺少本次执行边界证据时自动结算旧执行；该分支需另加测试，当前尚未复现完整普通任务场景。

## 4. 告警为什么会留在空界面

目前至少有四种不同来源，显示方式没有充分区分：

| 来源 | 当前情况 | 建议生命周期 |
|---|---|---|
| Host 配置不可信 | settings loading/error 独立拦截操作 | 持续展示，读取恢复后仍需重新启动授权 |
| 当前异常任务 | `UNRESOLVED` 汇总，另把 detail 复制到 `q.error` | 当前摘要由实际未处置任务推导，点击直达异常项 |
| 一次操作失败 | `viewStore.error` 在顶部显示；任意 `change()` 成功都会清除 | 绑定具体操作/表单/任务；相关操作恢复或用户关闭后收起 |
| 历史诊断、标题失败 | 任务 `detail/titleError` 持久显示 | 留在对应任务或执行记录；不要伪装成当前全局阻断 |

`updateActive()` 写入 `q.error`，而 `skip/retry/remove/adopt` 不收敛这个全局字段；Board 又无条件显示非空 `q.error`，故 R04 中异常已经不存在仍有红框。`recover()` 还可能为已启用但没有活动任务的队列写入“程序启动或连接切换”提示，该信息也被当作错误显示。

修复应按错误来源和是否仍有效决定显示，不能简单设定“队列为空就清除所有错误”：空队列时 Host 写入仍可能不可信。不要通过删除任务历史消除告警。成功完成后保留本次标题失败诊断是合理的；R07 的问题是重试后的旧诊断缺少 Attempt 归属，需要保留为“第 1 次执行的标题失败”，而非当前执行错误。

## 5. 异常之后能否执行后面的任务

**可以在人工处置异常并明确启动后继续；当前规则禁止默默越过异常。** [next / updateActive](../src/queue.ts) 和 `Coordinator.enable()` 均明确执行这条约束。失败可能包含命令已提交但回包丢失、旧 Session 仍在修改同一工作区等情况，仅有“报错”不足以判断可以启动下一项。

建议保留这条边界，先解决操作难理解的问题：

| 操作 | 实际含义 | 建议展示 |
|---|---|---|
| 打开 Session | 查看旧会话，无命令提交 | 查看原会话 |
| 继续原 Goal | 同一 Session、同一 Goal 的 `/goal resume` | 继续原目标；只在可恢复且空闲时提供 |
| 重新排队 | 保留旧 Attempt，创建新 Session，重新执行完整任务；仍在原队列位置 | 重试此任务（新会话），明确会重新执行任务 |
| 人工跳过 | 不标成功，保留已处置证据 | 跳过此任务，解释仍需启动队列才能派发后续 |
| 删除 | 移除允许删除的队列记录 | 删除记录；不能替代异常处置，也不等于停止 Session |

推荐用单个 **“查看并处理”** 入口，先只读核实连接代际、旧 Session 运行态和 Goal ID，再给出可用操作及不可用原因。动作提交前仍需再次核实，并保持原子恢复 claim；前置展示不能替代提交时校验。

当前 `interrupted` 显示“待人工恢复”，但普通任务没有原 Goal 恢复能力，建议改为“待核实”。恢复按钮当前只依据本地 `goalMode/sessionId/status` 出现，实际不能恢复时才弹错；应先解释真正可恢复条件。跳过和重排也不宜先弹笼统确认、再发现旧 Session 正在运行。

处置后的反馈必须说明下一步：“已跳过，队列仍暂停。点击‘启动队列’继续待执行任务。”恢复原 Goal 也不授予后续任务派发权。此轮不引入默认自动跳过、失败继续开关或隐式启动。

后续若要讨论“外部会话失败是否应阻断无关工作区”“确定尚未提交的失败能否允许后续先执行”，需要独立定义任务依赖、工作区冲突和失败分类，并修订现有规则；当前数据不足以支持直接放宽。

## 6. 控件和说明如何精简

### 标题区：合并表达，保留真实选择

“留空就由模型生成”不是当前统一行为：普通模式可能走原生标题路径，但不保证 AI 标题服务存在；纯 `/goal` 不触发首条用户消息命名。勾选 `generateTitle` 才是插件额外的一次独立模型请求。

建议统一为一个“标题”区，采用“留空 / 手动填写 / AI 生成”的命名方式选择：默认继续保持不额外生成；选择手动后显示输入框，选择 AI 后显示“一次额外模型请求”，长度默认 24，放进高级选项。不额外生成与手动输入均映射为 `generateTitle=false`，无需为界面模式建立第二份持久状态。

- 不再重复使用“可留空”和整段原生命名机制解释来表达同一个选择。
- 切换 AI 模式保留手动标题草稿；现有勾选行为直接 `setTitle('')`，取消勾选也不能找回原输入。
- 缺少真实标题统一显示“未命名任务”或“未命名目标”；不要在已失败/已完成的普通任务上仍显示“等待 DSH 自动生成标题”。
- 当前手动标题只是队列字段，派发没有将它重命名到原生 Session；不要承诺二者一致。若要增加同步，应另核验公开重命名与冲突策略。
- 如果产品以后选择“留空默认 AI 生成”，须明确这是默认成本、请求次数和启动时延的变化；本次不作此变更。

### 表单：任务内容优先，辅助选项后置

建议顺序：任务说明 → 工作区 → 执行方式 → 模型与推理 → 标题 → 高级选项。

必须保留工作区、任务内容、执行方式、模型配置和推理档位。模型目录刷新可放在目录错误处或设置区；标题长度放高级选项。“固定当前配置 / 执行时跟随 Host 默认”仍是有效选择，不能省掉后偷偷改变模型来源。

模型副作用用一行准确提示：“执行时设置模型也会更新 Host 默认模型。”原生投影、CAS、token、UTF-16 等实现说明移至帮助或详情；长输入限制实际触发时，在标题区解释“任务内容过长，无法额外生成标题；可关闭 AI 标题后保存”，不建议用户为了标题删掉任务正文。

保存错误应放到对应字段或表单内；现在 `onSave` 把错误送到背后的全局红框，模态层打开时不利于定位。禁用保存时需给出原因。该可见性与键盘体验仍须真实渲染验证。

### 列表与顶部：只保留当前决策需要的信息

- 顶部展示：队列授权状态、并发占用、待执行、待处理异常、同步新鲜度。主操作按情况显示“处理 N 项异常”或“启动队列”；后者仍是明确授权动作。
- “有 N 项异常”可直接切到异常分类，分类本身也显示数量，避免默认“待执行与运行”隐藏异常内容，只留下禁止启动的提示。
- 当前行主要展示标题、工作区、状态、必要原因和可用主操作；模型详情、时间戳、Attempt、完整 Session ID 放到展开详情。
- 不适用的上移/下移/编辑按钮不必在每个历史任务上保留灰色占位；异常动作给出理由，其他操作放“更多”。
- 复用历史 Session 的 `sessionActivity` 必须有独立的可查看活动入口，删除历史任务不应使占用变成无法打开的数字。
- `activeIds` 包含尚未创建 Session 的 starting claim，不能把所有占用都叫“运行中的会话”。区分“启动占位”“已观察运行”，总数仍只表示本客户端掌握的占用。
- 顶部常驻解释可缩为“暂停只停止派发，已运行任务继续。”完成判据与代码验收边界放详情/帮助，发生异常时再给下一步操作。

## 7. 另外两处应纳入范围的操作问题

### 7.1 默认工作区与保存后执行不够明确

`newForm()` 默认选 `workspaces.items[0]`，并不证明它是用户当前操作的工作区。建议从官方公开 UI 状态确认当前工作区；不能确认时要求明确选择，不能靠列表第一项猜测。

队列已授权时，新增任务可立即执行，表单按钮仍统一叫“保存”。建议该状态改为“加入运行中的队列”，并在保存前提示“加入后将按可用名额执行”；已启用但无待执行项时显示“等待新任务，加入后会执行”。这能保留既有语义又避免把保存误解为只存草稿。“排空后自动暂停”属于另一个产品行为变更，本轮不默认采用。

### 7.2 预检失败与提交结果未知被混为一类

`dispatch()` 对工作区已删除、模型目录不可用等创建前错误，也会落到“Session 创建未确认”的通用描述；没有 Session ID 时又不能重排，用户只能核实后跳过并新建。

应先准确区分“确认尚未提交”“确认旧会话已停止”“是否提交未知”。只有具有持久执行阶段证据的未提交失败，才可讨论提供“修改后重新排队”的简化路径；不能仅凭错误字符串判断安全。补充阶段信息时必须随任务/Attempt 同一次 CAS 保存，并覆盖旧数据迁移；未知情况继续保守处置。

需要新增的测试重点是事件与操作链，不能仅补文案字符串快照：

1. 已成功读取 → 下一次列表读取失败 → 旧目录仍 ready → 禁止新派发 → 读取恢复 → 仍需手动启动。
2. 面板开启/关闭期间外部 Session 新增、停止、复用；扫描中再次新增；同 ID 去重；Subagent 不作为主任务。
3. Goal A 中断 → 同 Session 改为 Goal B → B 完成，A 不能被自动结算；原证据完整。
4. 异常 → 原 Session 核实 → 跳过/重试/恢复 → 告警收敛与历史保留；同时存在多个异常、标题警告或 Host 错误。
5. 活动历史 Session 的旧任务被删除，活动仍可查看；占用直到权威运行态结束才释放。
6. 真实组件中执行分类切换、处置、重复点击、表单错误定位与标题模式切换；现有 `queue-view.test.ts` 只证明筛选，不证明这些交互。
7. 原 Session 运行中拒绝处置，CAS/命令回包丢失不补发，重连撤销授权，原 Goal 恢复保持一次执行权，原始多行任务不变。

本轮保持现状的边界：不自动重跑，不默默跳过失败，不删除执行证据，不默认增加标题模型请求，不声称跨 Client 全局并发保证，不修改 DPH 内置代码。
