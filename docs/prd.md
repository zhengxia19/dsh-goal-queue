# PRD：dsh-goal-queue 优化变更 U01–U13（2026-10-24）

> 需求基线：[项目优化分析与变更清单_2026-10-24.md](./项目优化分析与变更清单_2026-10-24.md)。本 PRD 不替代[原变更总调度](./change-plan-2026-10-20/00-总调度与验收.md)，原 T13 实机验收整合进 U12。

## 1. 项目背景与目标

**产品**：`dsh-goal-queue` v0.3.2-preview.0 —— DPH v0.2.1-rc.2 的原生多 Session 任务队列插件（可选无工具 AI 标题）。

**项目位置**：`D:\Code\dsh-goal-queue`，分支 `main`，基线 HEAD `69b675f`（工作树干净、已推送）。所有文档与代码变更均在此仓库内。

**本轮目标**（按清单结论排序）：

1. 先修复**会话身份与同步可信性**（U01、U02，P0）——完成证据归属错误与"旧目录冒充新基线"是最高风险。
2. 再修复**发现同步、告警收敛与异常操作**（U03–U08、U13，P1）。
3. 最后**精简表单、按钮与说明文字**（U09–U11，P2）。
4. 以 **U12 整合回归 + 真实 Host/Desktop 验收**收尾（P1，含老板实机确认项）。

**成功判据**：清单第 1 节 R01–R07 七个诊断探针场景全部由 Red 转 Green；`npm test` / `npm run typecheck` / `npm run build` / CI 通过；既有 96 项测试不回归；边界全部保持。

## 2. 范围与不可违反的边界

以下边界为产品约束，任何一环（架构/任务/代码/QA）不得突破：

| # | 边界 | 含义 |
|---|---|---|
| B1 | 不自动重跑 | 失败任务不自动重新派发 |
| B2 | 不默默跳过失败 | 异常必须人工处置并显式"启动队列"后才继续 |
| B3 | 不删执行证据 | 不得通过删任务历史消除告警；旧 Attempt 证据保留 |
| B4 | 不默认增加标题模型请求 | 默认仍不额外生成标题；AI 标题是用户显式选择的一次独立请求 |
| B5 | 不声称跨 Client 全局并发保证 | 占用数只表示本客户端掌握的占用 |
| B6 | 不修改 DPH 内置代码 | 只用官方公开契约（SDK/公开 UI 注入），不补丁 Desktop、不访问私有 manager |
| B7 | 串行派发（U13，本轮新增硬性需求） | 并发上限固定为 1：队列同一时刻至多派发/运行一个任务占用执行；显式启动授权保留，不自动重跑 |

**明确不做**（清单已定）：排空后自动暂停、默认"留空即 AI 生成"、手动标题同步到原生 Session 重命名、放宽"外部失败阻断无关工作区"、为性能猜测引入虚拟列表。

## 5. 需求分析：证据 → 根因 → 变更映射

清单第 1 节 7 个探针（R01–R07，均 Red，探针在 `.artifacts/optimization-analysis-2026-10-24/behavior-probes.mjs`）与变更的对应：

| 证据 | 现象 | 根因（清单结论） | 对应变更 |
|---|---|---|---|
| R01 | 新外部运行 Session 目录事件后计数仍 0 | 已纳入 Session 与新增发现走不同路径；目录订阅只调 `syncTitles()` | U03 |
| R02 | 刷新失败后旧 `phase=ready` 目录仍被信任 | SDK `refreshList()` 失败不改 `phase`；对外未投影内部 `state/error` | U02 |
| R03 | 恢复 CAS 未返回时发现被拒且不重试 | `settings.status=ready` 与 `booted=true` 间入口竞态；effect 不随 `booted` 重跑 | U03 |
| R04 | 异常已不存在仍有红框 | `q.error` 由 `updateActive()` 写入，处置操作不收敛该全局字段 | U05 |
| R05 | 旧任务 Goal ID 被同 Session 另一 Goal 替换并误结算 | `adopt()` 用 `data.goalId ?? t.goalId`；`observeTask()` 按替换后 ID 判完成 | U01 |
| R06 | 有占用却无可查看活动 | 复用历史 Session 的 `sessionActivity` 无独立入口；删记录后占用失联 | U04 |
| R07 | 重试后旧 `titleError` 缺 Attempt 归属 | 旧诊断未标注"第 N 次执行" | U05 |

**分析类结论（非缺陷但纳入需求）**：异常后"人工处置 + 显式启动可继续、禁止默默越过"是既有正确边界，保留（B2）；本轮解决的是操作可理解性（U06）。

**依赖关系**：U01 是 U03/U06 的身份前提（先保证不串身份，再扩大自动发现）；U02 是 U03/U05 的可信性前提（先保证目录可信，再谈同步状态展示与告警收敛）；U05 的 schema 调整应在 U07 的 Task/Attempt schema 之前定稿，避免两次迁移；U13（串行派发）与 U04/U06 同阶段——容量槽位收敛直接影响 U04 的占用展示与 U06 的启动语义，设计须一并定稿；U09–U11 均为 UI 层，依赖 P0/P1 行为稳定后进行。

## 6. API / 公开契约设计要求（交架构师）

本项目是 Cordis 插件，无自有 REST API；"API 设计需求"指对 DPH SDK 公开契约的使用要求：

| 契约 | 要求 | 用于 |
|---|---|---|
| `remote.session.list({}, signal)` → `RemoteResult` | 作为可验证新目录基线的取得方式（返回类型见已安装 SDK `lib/typert.remote-client.d.ts`） | U02 |
| `sessions.refresh / list / retain` 公开状态 | 与上述基线协调；`phase==='ready'` 仅表示"至少成功取得过一次"，不得当作本次刷新成功 | U02、U03 |
| **禁止** `sessions.list.getSnapshot().state` | 不属于当前公开契约；不访问私有 manager | U02 |
| 官方公开 UI 状态 | 确认用户当前工作区；不能确认时要求明确选择，不猜列表第一项 | U08 |
| Task/Attempt 持久化 CAS | 阶段信息必须随任务/Attempt 同一次 CAS 保存；覆盖旧数据迁移；旧数据不得伪造未提交证据 | U07、U05（必要时 schema） |
| 恢复 claim | 原子恢复 claim 不退化；恢复原 Goal 不授予后续派发权 | U06 |
| 标题路径 | `generateTitle=false` 统一映射"不额外生成/手动"；AI 标题为一次独立模型请求，长度默认 24 | U09 |

## 7. 测试与验收要求

清单第 8 节 7 条测试重点为**必做项**（事件与操作链测试，不能只补文案字符串快照）：

1. 成功读取 → 下次列表读取失败 → 旧目录仍 ready → 禁止新派发 → 读取恢复 → 仍需手动启动。
2. 面板开/关期间外部 Session 新增、停止、复用；扫描中再新增；同 ID 去重；Subagent 不作主任务。
3. Goal A 中断 → 同 Session 改 Goal B → B 完成，A 不被自动结算；原证据完整。
4. 异常 → 原 Session 核实 → 跳过/重试/恢复 → 告警收敛与历史保留；多异常 + 标题警告 + Host 错误并存。
5. 活动历史 Session 旧任务被删，活动仍可查看；占用直到权威运行态结束才释放。
6. 真实组件中分类切换、处置、重复点击、表单错误定位、标题模式切换（现有 `queue-view.test.ts` 只证明筛选）。
7. 原 Session 运行中拒绝处置；CAS/命令回包丢失不补发；重连撤销授权；原 Goal 恢复保持一次执行权；原始多行任务不变。
8. （U13 新增必做）多任务待执行：启动队列后仅第一个进入运行；其完成或失败被处置后下一个才获派发；任何路径（含恢复、重连、并发点击）不得出现两个任务同时占用 Session 执行。

**U12 整合验收（与原 T13 合并）**：新故障回归、旧数据迁移、去重、并发、恢复、空标题；`npm test` / `npm run typecheck` / `npm run build` / 远端 CI；两工作区含中文路径；独立复核；保留未执行项记录。

**老板实机确认项（自动化无法覆盖，验收前必须列出交 Chief 转老板）**：真实 DPH Desktop 安装/加载、真实 Host 下的发现与派发、多工作区实机操作、键盘/焦点/窄窗实测、R03 在 Desktop 的实际触发时序。

## 9. 竞品分析（定性）

本轮为既有插件的可信性与体验修复，竞品对照用于确认产品定位，不引入新功能：

| 对照 | 形态 | 与本产品差异 | 对本轮的启示 |
|---|---|---|---|
| DPH 原生 Session 列表（基线） | SDK `SessionListManager`，`phase` 只表示"曾成功取得过目录" | 原生不提供任务队列、派发授权与 Attempt 证据 | 插件的可信性必须建立在公开契约语义之上（U02 不得假设 `ready`=本次成功），这是与"简单包一层原生列表"的本质区别 |
| Cursor 后台 Agent / 任务队列 | 云端并行编码任务管理 | 托管环境，无本地多 Session 复用与恢复语义 | 队列+Session 绑定是同类产品的通用形态；身份归属与失败处置是同类痛点，本产品以 fail-closed 授权与证据保留为差异点 |
| Conductor / vibe-kanban 类多 Agent 编排工具 | 并行 Agent 任务看板 | 面向 Agent 编排，非 DPH 原生插件；无 Host 授权代际概念 | 看板"异常直达、行操作分层"是成熟形态，支持 U06/U11 的方向；但本产品边界（不自动重跑、不默默跳过）更保守，属有意差异 |

结论：本轮变更方向（身份可信 → 同步可信 → 告警按来源 → 操作可理解 → 精简）与同类产品演进路径一致，且保守边界（B1–B6）是本产品既有卖点，全部保留。
