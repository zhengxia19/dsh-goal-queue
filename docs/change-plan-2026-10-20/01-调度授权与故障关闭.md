# 01｜调度授权、Pause 竞态与 Host 故障关闭

> 阶段目标：消除“用户暂停但任务仍提交”“启动中占位泄漏”“写入故障后读回自动继续”三类路径。**必须按 T01→T02→T03 顺序实施**，每一项独立 Red→Green。当前 T01–T03 的源码验证完成。

## T01 暂停与占位的原子边界

- [x] **T01 源码与 CI 验证完成；前置：完成基线核验。**

### 问题与现有源码

- 已存在 `Coordinator.enable()`（`src/client/coordinator.ts:102–119`）、`Coordinator.pump()`（120–150）、`claim()`（`src/queue.ts:109–112`）。
- `pump()` 先 `await this.write(q=>claim(...))`，然后才检查 `this.armed`。用户调用 `enable(false)` 会提前设 `this.armed=false`。结果可能是**已持久占位但未派发**；该路径缺少释放操作，任务仍为 `starting`。
- 现有 `test/recovery-regression.test.ts` 的“Start 后立刻 Pause”只验证没有新 Session；它不能覆盖 pause 恰好落在 `claim` 写入过程或写入完成之后的交错时序。

### 明确的源码动作

| 类型 | 目标 | 工作内容 |
|---|---|---|
| **修改** | `Coordinator.enable()`、`pump()` | 为手动启停和一次 dispatch 建立明确的调度授权代际/提交门禁；Pause 的成功反馈之前确保不可撤销边界清晰；不得用重新启用覆盖旧的撤销决定。 |
| **修改** | `src/queue.ts` 的 `claim()`、`updateActive()` 或状态转换入口 | 保证 `starting` 只在确有受控派发操作时持有槽位，明确未创建 Session 与已创建 Session 的不同回滚规则。 |
| **建议新增** | 例如 `releaseUnsubmittedClaim()` 或等价纯状态转换 | **仅在证明远端尚未创建/提交时**释放占位、恢复 `pending`；不得把未知结果当作未执行。 |
| **新增测试** | `test/recovery-regression.test.ts` 或 `test/coordinator.test.ts` | 用可控 Promise 挂起 Host `settings.set()`，精确插入 Pause，而不是使用随机 `sleep()`。 |
| **保留** | `activeIds`、`maxConcurrent`、重启 `recover()` | 不破坏旧 `activeId` 兼容和运行中的 Session 不被暂停按钮取消的规则。 |
| **删除** | 无 | 不删除旧字段、任务或 Session 记录。 |

### 验收（全部通过才能勾选）

1. **Red**：构造 `claim` 写入期间 Pause 的可重复交错，在修复前观察至少一个确定的占位泄漏或不符合期望的派发时序，并保存测试日志；如模拟基础设施不能复现，记录原因并修订用例后再实施。
2. **Green**：收到 Pause 确认后，尚未越过执行提交边界的待执行任务没有新的 `session.prompt()` / `/goal` 调用。
3. 已确定尚未创建 Session 的 claim 回到 `pending` 且不占 `activeIds`；不能产生永久 `starting`、负数并发容量或无法人工处置的项目。
4. 旧 Session 已在运行时 Pause 不终止、取消或重新创建它；并发数降低行为不变。
5. Start/Pause/Start 快速交错、两个不同任务并发 claim、`maxConcurrent=1/2` 情形均通过负向用例。
6. `npm test`、`npm run typecheck`、`npm run build` 全部退出码 0，留存 Red→Green、commit SHA、复审结果。

### 完成后的不可跳过检查

源码中所有写入 `starting` 的路径都必须有明确的后续状态出口；检查 `setSessionId()` 失败、连接切换和配置刷新时不会自行解除安全阻断。

## T02 Session 创建和辅助标题期间的暂停

- [x] **T02 源码与 CI 验证完成；前置：T01 验收通过。**

### 问题与现有源码

- `Coordinator.dispatch()`（`src/client/coordinator.ts:162–211`）先 `sessions.create()`，再可选提交 `/goal-queue-title`，最后提交执行性的 `/goal` 或 `session.prompt()`。
- `enable(false)` 改变 `armed`，但 `dispatch()` 当前只检查 `generation/closed/connected`，没有统一的 Pause 提交门禁。
- `submitted=true` 只在执行性命令调用之前设置，异常后可以进入 `interrupted`；需要精确区分“不曾尝试发送”和“远端可能已接受”。

### 明确的源码动作

| 类型 | 目标 | 工作内容 |
|---|---|---|
| **修改** | `Coordinator.dispatch()` | 在创建 Session、标题请求、执行性命令前后核对同一轮调度授权；保持一次性不可重复提交边界。 |
| **修改** | `Coordinator.enable()`、`fail()`、`quarantine()` | 用户暂停不自动停止正在运行的 Agent；若执行性命令已发送或提交结果未知，显式保留相应状态和 Session 证据。 |
| **建议新增** | `DispatchPhase` / `DispatchPermit` 等辅助概念 | 用状态而非单个 `submitted` 布尔变量记录“未创建”“Session 已创建但未提交任务”“提交结果未知”“已提交”；名称与实现由实测确定。 |
| **修改** | `QueueBoard.tsx` 必要时增加文案 | 用户能区分“暂停新派发”和“已提交任务仍在运行”；不宣称 Pause 可撤销已进入 Host 的命令。 |
| **新增测试** | `test/coordinator.test.ts`、`test/recovery-regression.test.ts` | 延迟 `sessions.create()`、`retain().ready`、模型标题命令与真正执行性 RPC，分别插入 Pause/Reset。 |
| **保留** | `registerTitleCommand()` 无工具 LLM 与 `sessionTitle.rename()` | 不为了修复竞态而引入普通 Prompt 或重复标题请求。 |
| **删除** | 无 | 不静默移除已创建 Session 的关联。 |

### 验收

1. **Red**：分别在 `sessions.create()`、`hold().ready`、`/goal-queue-title` 等 Promise 被挂起时点击 Pause，确认旧实现至少存在一次迟到的执行性命令提交窗口；截图/日志保存到 T02 证据目录。
2. **Green**：对**尚未越过提交边界**的任务，Pause 后执行性调用计数保持 0；如果创建了新 Session，必须保存其 ID 并给予明确的安全终态或隔离说明，不产生无记录的孤立执行。
3. 对**已越过提交边界**的任务，Pause 只阻止之后的新任务，不自动重发、不声称取消远端 Agent；超时/未知响应必须进入人工核实而非 `pending`。
4. 标题请求失败后正常执行原任务的既有降级路径保留，但当授权已经撤销时不能因标题失败/完成继续提交新的 `/goal` 或 Prompt。
5. Reset/关闭 Client/取消标题请求的竞态不得留下当前连接可继续派发的旧授权。
6. 新增 Red→Green 测试和全套 `npm test`、`typecheck`、`build` 成功，逐项留证。

## T03 Host 错误后的调度失效

- [x] **T03 源码与 CI 验证完成；前置：T02 验收通过。**

### 问题与现有源码

- `HostQueueSettings.set()`（`src/client/settings.ts:90–120`）可发布 `status='error'`，`HostQueueSettings.refresh()` 成功后发布 `ready`。
- `Coordinator.start()` 的配置订阅只调用 `pump()`，没有在快照进入 `error/loading` 时统一撤销 `armed`。如果用户在此前已启用队列，刷新恢复为 `ready` 后存在未经再次人工授权的继续派发窗口。

### 明确的源码动作

| 类型 | 目标 | 工作内容 |
|---|---|---|
| **修改** | `Coordinator.start()` 的 settings 订阅；`Coordinator.pump()` | 任意配置失信事件使调度授权立即失效，重新读取成功不能恢复授权；新派发必须再次手动点击“启动队列”。 |
| **修改** | `HostQueueSettings.failClosed()`、`refresh()`、`set()`（必要时扩展快照） | 明确向 Coordinator 传播读失败、写失败、CAS 冲突、结果未知与连接 reset；读回数据只做状态恢复，不直接视作用户授权。 |
| **建议新增** | 配置可信代际、授权代际，或等价状态约束 | 确保旧 Host 的 `ready` 事件不能误激活新 Host 的队列。 |
| **修改** | `QueueBoard.tsx` 的错误/启动提示 | 读取恢复后显式提示“需要重新人工启动”，有未决 `interrupted/blocked/failed` 时仍必须先处置。 |
| **新增测试** | `test/settings.test.ts`、`test/recovery-regression.test.ts` | 已启用状态下的 UI 编辑 CAS 冲突、写入异常、刷新成功、订阅回调、连接切换。 |
| **删除** | 无 | 不在错误时回退到 `DEFAULT_SETTINGS` 空队列并提交写入。 |

### 验收

1. **Red**：队列已启用，制造非调度路径（如 `add()`/`move()`）的 CAS 失败，再恢复 `refresh()`；修复前可证明 `armed` 未撤销或发现不期望派发窗口。
2. **Green**：所有失败路径都使本 Client 调度权失效；即使 Host 返回 `queue.enabled=true`，新 Session 创建数仍保持 0，直到用户再次显式启动。
3. CAS 冲突、timeout after commit、失败后成功 `refresh()`、连接 `reset` 旧响应迟到、新旧 generation 竞争，都有精确负向用例。
4. 读取错误页面不显示假的空队列，不允许变更；恢复读取后真实 tasks、Session ID、顺序完整保留。
5. 失败关闭不会误停止已经运行的 DSH Agent；既有 Agent 的观察权由恢复扫描安全建立，不能隐式二次提交。
6. 单测/类型检查/构建全通过；本阶段的 T01–T03 证据复审完成后才进入 02。
