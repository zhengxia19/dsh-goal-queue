# 02｜原 Session 恢复、人工处置与 Goal 题词完整性

> 阶段目标：原 Goal 恢复最多提交一次、阻塞/暂停 Goal 可继续、重新排队/跳过必须有 Host 会话证据、Goal 题词不被无意压缩。**T04→T05→T06→T07**，须在 T01–T03 自动化与复核全部通过后开始。

## T04 Goal 恢复操作互斥

- [x] **T04 源码与 CI 验证完成；前置：T03 验收通过。**

### 真实源码定位与问题

- `Coordinator.resumeGoal()`（`src/client/coordinator.ts:324–354`）先读取旧任务，再异步 `retain()`、查询原 Goal 投影、`write(adopt())`、`hold()`，最后发送 `/goal resume`。
- `adopt()`（`src/queue.ts:141–151`）在相同 Session 的任务已 `running/starting` 时直接返回原队列；不能阻止两个早已通过 `status='interrupted'` 检查的 `resumeGoal()` 并发执行。
- `QueueBoard.tsx:131` 的按钮未使用恢复专用 `submitting` 状态，重复点击仍可能发起多次请求。

### 源码动作

| 类型 | 文件、现有对象 | 具体动作 |
|---|---|---|
| **修改** | `Coordinator.resumeGoal()` | 将“读取 Host 状态→获得一次性恢复权→保存占位→提交恢复命令”设计为有明确线性化点的状态机，第二个并发请求必须在提交前失败。 |
| **修改** | `src/queue.ts` 中 `adopt()` 或新增恢复专用转换 | 避免把重复恢复当作成功 no-op；禁止越过同一 Session 的恢复占位。 |
| **建议新增** | `claimGoalResume()`／`ResumeAttempt` 等纯转换或互斥结构 | 确保发生远端命令结果未知时不会“释放授权后重试”。建议命名并非已存在对象。 |
| **修改** | `QueueBoard.tsx` | 恢复处理中按钮置为不可再次提交，同时给出“处理中/需要核实”的明确状态；不能只依赖前端禁按钮。 |
| **新增测试** | `test/discovery-concurrency.test.ts`、`test/coordinator.test.ts` | 两次并发恢复、第一次持久写入延迟、`hold()` 延迟、未知命令结果。 |
| **删除** | 无 | 保留原 Session ID、Goal ID 和已记录的观察历史。 |

### 验收

1. **Red**：精确并发启动两个 `resumeGoal(sameTask)`，强制交错，使旧实现出现两次 `/goal resume` 入口调用或可重复的重复提交窗口。
2. **Green**：同一恢复授权只允许一次 `command('/goal resume')`；第二次必须返回可解释的“正在恢复/状态已改变”，不进入 Host 命令层。
3. `/goal resume` 发送前须检查原 Goal ID、可恢复 `phase`、Session idle 和容量；状态未知或 Host 断连不得自动再发。
4. `hold` 或持久化失败、远端执行可能已接受但回包未知时保留异常证据并阻止后继任务。
5. 不新建 Session，不额外发送普通 Prompt，不在 Client 重启后自动 resume。
6. Red→Green 与完整测试、typecheck、build 退出码均为 0，证据复审通过。

## T05 阻塞及暂停 Goal 恢复

- [x] **T05 源码与 CI 验证完成；前置：T04 验收通过。**

### 真实源码定位与问题

- `observeTask()`（`src/client/observe-task.ts:43–45`）对 Goal 的 `blocked/paused` 执行 `ops.fail('blocked')`。
- `QueueBoard.tsx:131` 和 `Coordinator.resumeGoal():326–327` 只允许任务处于 `interrupted`；因此运行中转为 `blocked` 的任务没有原 Session 恢复入口。

### 源码动作

| 类型 | 文件、现有对象 | 具体动作 |
|---|---|---|
| **修改** | `Coordinator.resumeGoal()` | 允许满足 Host 原生 Goal 恢复条件的 `blocked` 或 `interrupted` 任务进入 **T04 的同一个互斥入口**，不能增加另一条无锁恢复路径。 |
| **修改** | `src/queue.ts` 的恢复相关转换 | 对 `blocked` 转恢复中和最终状态作合法迁移；仍阻断整个队列自动派发直到用户明确处理。 |
| **修改** | `QueueBoard.tsx` | 符合条件才显示「继续原 Goal」；明确“继续原 Session”与“重新排队（新 Session）”的区别。 |
| **审查后可能修改** | `observe-task.ts` | 核实恢复命令后 `phase=active` 的真实变化，若现有观察器足够则不改；不得伪造 `phase=complete`。 |
| **新增测试** | `test/discovery-concurrency.test.ts`、`test/coordinator.test.ts` | blocked/paused、idle/running、Goal ID 匹配/不匹配、反复点击、容量满。 |
| **删除** | 无 | 不删除异常阻断状态或原生 Goal 投影校验。 |

### 验收

1. `blocked` 且旧 Session idle、Host Goal `phase ∈ {active, paused, blocked}`，可由用户明确操作在**相同 Session ID** 中发送一次 `/goal resume`；原生 API 如另有限制，以实际 Host 测试为准。
2. 活动中的旧 Session 不允许二次 resume，应引导用户刷新运行 Session；缺少 Goal、Goal ID 不符、`phase=complete`、并发满等路径显式拒绝。
3. 恢复失败/未知结果保留 `interrupted/blocked` 可诊断状态，不会让下一个 pending 自动启动。
4. 复用 T04 的互斥保证；正常恢复后只有 Host 报告 Goal complete + idle 才将本任务标记 `completed`。
5. 专项与全套测试、typecheck、build 通过，并保存实际测试场景证据。

## T06 重试与人工跳过之前的会话核验

- [x] **T06 源码与 CI 验证完成；前置：T05 验收通过。**

### 真实源码定位与问题

- `Coordinator.retry()` / `skip()`（`src/client/coordinator.ts:95–96`）直接转发到 `queue.ts:164–180`。
- `QueueBoard.tsx:132–139` 仅有浏览器 `window.confirm` 提醒，没有实时 Host Session `running` 检查；故障后旧 Session 可能仍在运行。

### 源码动作

| 类型 | 文件、现有对象 | 具体动作 |
|---|---|---|
| **修改** | `Coordinator.retry()`、`skip()` | 在调用状态转换前，从旧 `sessionId` 读取 Host 运行态和必要 Goal 投影；校验结果有效期及连接代际，并在实际写入前二次核对或用不可变观察令牌。 |
| **建议新增** | `inspectOriginalSession()`、`SessionDisposition` 等 | 返回“已停止且可处置 / 正在运行 / 不存在或无法核实”三类结果，不将异常简单视为 idle。 |
| **修改** | `queue.ts` 的 `retry()`、`skip()` | 接受可信处置前置证据或只允许 Coordinator 经明确验证的转换；不可让其他调用路径绕过安全门禁。 |
| **修改** | `QueueBoard.tsx` | 正在运行时禁用不安全操作；不可核实时显示原 Session ID、核实步骤与人工确认要求；提示文字不充当技术校验。 |
| **新增测试** | `test/coordinator.test.ts`、`test/discovery-concurrency.test.ts` | Session 仍运行、已空闲、无法 retain、scan 时连接 reset、点击重试后会话突然再次运行。 |
| **删除** | 无 | 不提供默认自动重复执行；不以“跳过”伪造 Goal 完成。 |

### 验收

1. 原 Session 仍在运行时，`retry`/`skip` 的业务状态写入拒绝执行，并提示原 Session ID；不得创建新的任务 Session。
2. 明确确认 idle 并满足稳定性判定后，允许人工重试或跳过；重试必须生成**新执行尝试**的语义，不能直接把原执行视为失败后可安全重发。
3. Session ID 缺失、不可访问或 Host 查询报错时，进入“不可核实/需人工证据”流程；禁止不知情的一键重试。必要的人工覆盖必须单独标注高风险且保存核实记录，不能等同于自动检查通过。
4. 校验完成到 CAS 写入前的连接切换/状态变化必须防竞态；不接受只在弹窗中核实而底层方法无校验。
5. 兼容旧 `interrupted/failed/blocked` 记录、导入 Session 无题词不可重发的规则；专项 Red→Green 和全套测试通过。

## T07 Goal 输入完整性

- [x] **T07 源码与 CI 验证完成；前置：T06 验收通过。**

### 真实源码定位与问题

- `Coordinator.dispatch()` 的 Goal 分支将 `task.prompt.replace(/\s+/g,' ').trim()` 拼进 `/goal`。此转换会删除多行代码和 Markdown 结构；普通 `session.prompt()` 则直接使用原 Prompt。
- `observeTask()` 对 Goal `objective` 也使用了同样压缩方式比对；修复提交编码时必须同步匹配逻辑，不能只替换调度层字符串。

### 源码动作

| 类型 | 文件、现有对象 | 具体动作 |
|---|---|---|
| **核实** | DSH `0.2.1-rc.2` 的 `Session.command()` 与 `/goal` 命令输入契约 | 确认多行输入、命令转义及 Goal 投影 `objective` 的实际规范化规则。禁止未经核实就把多行字符串直接拼接为 slash 命令并宣称无损。 |
| **修改** | `Coordinator.dispatch()` Goal 分支 | 选择官方支持的文本保真提交方式；不额外发送普通 Prompt、不创建额外 Agent Round。 |
| **修改** | `observeTask()` Goal objective 比对 | 按 Host 的真实规范化契约匹配提交目标，保留相同 Goal ID 验证，不以只比对标题取代。 |
| **建议新增** | `encodeGoalCommandInput()` 与正规化比对函数 | 如官方命令接口支持，封装编码与解码，避免随处 `replace(/\s+/g)`；新函数名仅建议。 |
| **新增测试** | `test/coordinator.test.ts`、`test/queue.test.ts`，必要时新的 Host 契约测试 | Markdown 列表、换行 Shell 代码块、双空格、中文、JSON、反斜线和命令样式文本。 |
| **删除** | 仅在确认替代契约有效后删除局部有损折叠调用 | 不删除原生 `/goal` 语义和完成判据。 |

### 验收

1. **先核实 DSH 命令契约**；如果官方 API 不能保真，须停在本任务记录阻断，不能用未经授权的合成普通 Prompt 绕过。
2. 对测试输入逐一比较“表单输入 → Host 命令接收 → Goal 投影 objective”，没有因本插件造成的结构丢失；如 Host 官方规范化不可避免，需在 UI 明示并保留原文证据。
3. 不增加任何额外执行性 Prompt；每个新任务只建立一个 Session、提交一个有效 `/goal`。
4. Goal ID/phase/idle 验证仍有效，正常模式原 Prompt 完全不受影响。
5. 所有专项测试、`npm test`、`npm run typecheck`、`npm run build` 通过，真实多行输入测试并入 T13。
